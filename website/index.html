Introduction

Reproducing a machine-learning paper requires more than generating plausible code. An agent must recover the target claim, respect the experimental contract, complete every required stage, and deliver artifacts whose reported metric can be independently checked. ReproBoundary evaluates this end-to-end capability across 47 frozen paper-to-code tasks.

Each task fixes the source repository and revision, data scope, required stages, target metric, reference value, expected outputs, and evaluator before the run begins. The public release connects every task definition to its source code, execution trajectory index, and verification record.

Scope. Each task reproduces one selected result under a frozen task definition. It does not reproduce every result or support every conclusion in the source paper.

Construction Pipeline

The benchmark is built as a traceable chain from one paper-reported result to a frozen task, a controlled run, and an independent check.

01

Select a target result

Freeze one concrete experiment, paper-reported reference value, public source repository, and exact code revision.

02

Define the contract

Record the data scope, required stages, expected outputs, target metric, evaluator source, and result format.

03

Run the agents

Execute every task with nine model-agent settings, producing 423 indexed trajectories across the 47-task pool.

04

Release and verify

Separate lightweight code from compressed logs, redact sensitive text, index file hashes, and provide deterministic integrity checks.

Task Taxonomy

Tasks are organized along three explicit dimensions instead of being reduced to a single difficulty label.

Research target

Each task isolates one paper-reported result, its reference value, the dataset used for final evaluation, and the exact source-code revision needed to interpret it.

Research domain

The pool spans 15 domains, including language models, multimodal learning, computer vision, reasoning, safety, reinforcement learning, time series, graph learning, retrieval, and scientific machine learning.

Verification contract

Every task binds one target metric to its dataset, required outputs, evaluator source, evaluator version, and expected result format.

Evaluation Framework

Evaluation Protocol

ReproBoundary does not treat a plausible report or a matching number as sufficient evidence of reproduction.

Execution

Did the run complete every stage required by the frozen task specification?

Delivery

Are the expected outputs, provenance records, and supporting artifacts present and traceable?

Metric replay

Can the task-specific evaluator recompute the submitted target metric from the required artifacts?

Agreement

Does the recomputed metric agree with the submitted value under the task's declared comparison rule?

Important. Metric agreement confirms a number; it does not by itself prove that every required experimental stage was completed. Process evidence and metric evidence remain separate.

Verify the Release

GitHub hosts the lightweight task definitions, evaluator records, protocol templates, and verification code. Hugging Face hosts 423 cleaned, compressed execution logs. Both surfaces link back to this website and to each other through their release documentation.

git clone https://github.com/ReproBoundary/ReproBoundary.git
cd ReproBoundary
python3 scripts/verify_release.py

# verification OK: tasks=47 evaluators=47 trajectory_records=423 bundled_logs=0

Evidence boundary. The logs support chronology, tool-use, failure, and release-integrity analysis. They do not include checkpoints, predictions, model weights, or training states and cannot by themselves replay most scientific metrics.

Experimental Results

Main Results

Across the frozen 423-run cohort, 101 runs completed the required execution stages and 78 met the stricter end-to-end reproduction criterion. The strict ledger contains 78 successes, 338 failures, and 7 unresolved cases.

The strongest configuration, gpt-5.6-sol + codex, achieved 21 strict successes out of 47 tasks (44.7%). The next configuration achieved 11/47 (23.4%). These figures describe this fixed task pool and protocol; they are not general model capability scores.

Interpretation boundary. The 101/423 execution count and 78/423 frozen strict count are different views. Neither replay match nor successful delivery alone establishes strict reproduction.

Submit a Run

A reported metric is not a submission. Package the frozen contract, all six protocol deliverables, and the evidence needed to replay the result.

Required package

<project-id>-<model>-<agent>/
├── TARGET_EVALUATION.json       # exact assigned contract
├── DATASET_SELECTION.json       # frozen scopes and selected-ID hashes
├── pipeline-execution.json      # stages, commands, exits, times, artifacts
├── reproduction-report.md       # work completed, failures, limitations
├── audit.json                   # fixes and protocol-preserving events
├── metrics.json                 # metric, scope, evaluator, evidence path
├── security-attestation.json    # policy hashes and declared events
├── evidence/
│   ├── evaluator/               # raw official evaluator output
│   ├── logs/                    # execution logs and exit evidence
│   ├── outputs/                 # predictions and task-required outputs
│   └── intermediates/           # artifacts linking required stages
├── source/                      # commit id plus patch/diff, if changed
└── SHA256SUMS                   # hashes for every submitted file

Before sending

  1. Use the schema and filenames from the task's required_agent_output contract.
  2. Keep all evidence paths relative and ensure every referenced file is present.
  3. Run the official evaluator and retain its unedited output.
  4. Generate and verify SHA256SUMS; remove credentials, private paths, datasets, model weights, and unrelated files.

What we verify

  1. Contract identity, configuration identity, and hashes.
  2. Required stage order and artifact lineage.
  3. Completeness of the six JSON/Markdown deliverables.
  4. Independent replay of the target metric from submitted outputs.

Submit. Upload one .tar.gz package to a stable download link, then email the link, project ID, model, agent, source commit, and package SHA-256 with subject ReproBoundary submission: <project-id> / <model> / <agent>. See the full submission guide.
